## 2. 产品摘要

### 2.1 问题

用户在不同国家和电商平台搜索商品时，需要自行完成需求翻译、商品去重、库存核验、跨币种价格比较和证据检查。普通语义推荐还可能返回超预算、缺货、错误品类或配件类商品。

### 2.2 目标用户

第一阶段面向使用中文表达购物需求、希望比较多个市场报价，并要求推荐结果可核验的个人用户。

### 2.3 MVP 价值

Glodex 接收一条自然语言购物需求，在版本化商品快照中：

1. 提取当前请求的硬约束与软偏好；
2. 合并同一商品的多个市场报价；
3. 在排序前执行预算、品类、库存和商品本体硬门；
4. 按当前查询对合格商品排序；
5. 返回最多 3 个带价格、来源和证据的商品；
6. 无合格商品时明确说明原因，绝不擅自放宽预算或其他硬约束。

### 2.4 核心原则

- **硬约束优先**：预算、品类、库存和明确排除条件先于任何语义排序。
- **证据优先于文案**：系统只能陈述快照或确定性计算能够证明的事实。
- **不静默放宽**：零命中是合法结果；系统不能为生成推荐而修改用户硬约束。
- **Query-first**：MVP 只按当前请求排序，不引入长期用户画像。
- **确定性基线**：默认验收不访问网络、不调用真实 LLM、不依赖外部数据库。
- **可替换依赖**：模型、检索引擎和 Provider 均通过合同替换，不能改变业务不变量。

## 3. 主用户旅程

1. 用户输入自然语言请求，例如：
   “帮我找一台 800 美元以内、有库存、适合出差的轻薄本。”
2. 系统展示其识别出的硬约束和软偏好，并保留对应的查询原文引用。
3. 系统读取指定版本的商品与报价快照。
4. 系统合并跨平台同款商品，并计算可比较的到手价。
5. 系统过滤超预算、缺货、错误品类、配件类和关键证据不足的候选。
6. 系统按当前查询对剩余候选稳定排序。
7. 系统返回最多 3 个商品及其可用报价、选择理由、未知项和证据来源。
8. 如果没有合格商品，系统返回 `NO_MATCH` 和过滤原因统计，并请用户主动修改条件。

## 4. MVP 范围

### 4.1 In Scope

- 中文自然语言购物请求。
- 预算、目标品类、库存、明确排除项等硬约束。
- 使用当前请求产生的软偏好和查询相关度。
- 一个版本化、可校验的本地商品与报价快照。
- 至少 3 个 Provider/市场的离线报价数据。
- 同款商品 canonical ID 去重，保留各市场报价。
- 使用版本化汇率快照进行跨币种换算。
- 商品价、运费、税费和关税组成的可解释到手价；未知费用必须显式标记。
- 硬约束过滤、商品本体检查、稳定的 Query-first 排序。
- 最多 3 个带证据的结构化推荐结果。
- `NO_MATCH`、输入错误、数据错误和降级状态。
- 可重复执行的离线验收用例、运行 ID 和阶段级诊断。
- 一个稳定的领域输入/输出合同；传输层由后续 Plan 选择，不得改变该合同。

### 4.2 Out of Scope

以下能力属于目标架构或后续里程碑，不进入 M0：

- 实时抓取或调用真实电商平台。
- 实时汇率、实时税费或完整海关规则引擎。
- 自主 ReAct AgentLoop、子 Agent fork 和开放式工具选择。
- Category Insight、长期记忆、用户 ANN 和画像冲突 Judge。
- OpenSearch、向量数据库、cross-encoder 和 embedding 训练。
- 查询自动改写与 Reflect 恢复循环。
- Postgres 任务队列、持久 checkpoint、Redis 缓存和多 Worker。
- AG-UI/WebSocket、React 前端和生产部署。
- 自托管 vLLM、SFT、Agentic RL。
- 对真实商品覆盖率或生产推荐质量作出承诺。

## 5. 术语与业务规则

| 术语 | 定义 |
|---|---|
| Required | 用户当前请求中必须满足的条件；必须能引用查询原文或来自显式结构化输入。 |
| Preferred | 用于排序但不能过滤候选的偏好。 |
| Canonical Product | 去除平台差异后的商品主体；由稳定 `product_id` 标识。 |
| Offer | 某 Provider/市场针对一个 Canonical Product 提供的报价、库存及证据。 |
| Eligible Offer | 满足市场、库存、费用可证明性等要求的报价。 |
| Landed Cost | 商品价、运费、税费和关税按版本化汇率转换后的总价。 |
| Evidence | 能支持一个输出事实的快照字段、计算输入、来源标识和采集时间。 |
| Query-first | 召回和排序由当前请求驱动，不使用长期用户偏好改变候选池或最终分数。 |
| `NO_MATCH` | 已成功执行搜索，但没有候选满足所有硬约束。它不是系统错误。 |
| `FAILED` | 输入、数据合同或执行过程无法产生可信结果。 |

业务规则：

1. Required 条件只能由当前查询或显式输入产生，Preferred 不得升级为 Required。
2. 所有硬门必须在排序之前执行，排序不得把被过滤商品带回。
3. 预算比较使用 Landed Cost，而不是只比较商品标价。
4. 当预算是 Required 且 Landed Cost 的必需组成部分未知时，该报价不能被证明在预算内。
5. 一个商品可以保留多个 Eligible Offer，但结果列表中只能出现一次。
6. 商品主体不匹配时，即使标题文本高度相关也不能进入结果。
7. 未被 Evidence 支持的规格、价格或推荐理由不得出现在输出中。
8. 相同输入、快照、配置和实现版本必须产生相同排序。
9. M0 的推荐报价必须为 `IN_STOCK` 且能够计算完整 Landed Cost；这是系统资格条件，不会在用户未明说时伪造成 Required。
10. 预算门只在存在 `BudgetMax` 时启用；没有预算不等于允许未知费用报价进入结果。
11. 查询明确给出预算币种时，以该币种的精确金额比较；未给出币种时使用 `display_currency`。结果仍以 `display_currency` 展示。
12. query、locale、top_k 和币种格式在创建 run 前校验；snapshot 是否存在以及币种是否被该 snapshot 支持在 run 内校验。

## 6. 领域输入与输出合同

### 6.1 最小输入

| 字段 | 必填 | 规则 |
|---|---:|---|
| `query` | 是 | UTF-8 文本；去除首尾空白后长度为 1–2000。 |
| `locale` | 否 | M0 默认且只验收 `zh-CN`。 |
| `display_currency` | 否 | 默认 `USD`；创建 run 前校验三字母格式，创建 run 后校验它存在于指定汇率快照。 |
| `top_k` | 否 | 默认 3；M0 允许 1–3。 |
| `snapshot_version` | 否 | 未指定时使用配置的默认版本，并在输出中回显。 |

### 6.2 最小输出

成功或无匹配结果必须包含：

- `run_id`
- `status`: `COMPLETED`、`NO_MATCH` 或 `FAILED`
- `snapshot_version`
- `interpreted_request`
  - `required[]`
  - `preferred[]`
  - 每项的 `source_span`
- `results[]`
- `filter_summary`
- `warnings[]`
- `diagnostics`

每个 `results[]` 项至少包含：

- `product_id`
- `title`
- `category`
- `selected_offer`
- `eligible_offers[]`
- `landed_cost`
- `matched_requirements[]`
- `unknowns[]`
- `reason`
- `evidence[]`

`reason` 只能重述已验证事实及确定性评分信息，不能生成快照中不存在的产品能力。

## 8. 验收数据集

M0 的版本化 fixture 至少包含：

- 30 个 Canonical Product；
- 至少 3 个商品品类；
- 至少 3 个 Provider/市场；
- 至少 3 种报价币种；
- 同款跨平台重复记录；
- 预算内、超预算、缺货和未知费用报价；
- 商品主体、配件、替换件和误导性 listing；
- 缺少 ID、来源或证据的脏记录；
- 至少一个 Landed Cost 完全相同、需要稳定 tie-break 的候选组。

数据必须可提交、可审查、可版本化，不包含访问真实平台所需的密钥或用户数据。

## 9. Given-When-Then 验收场景

### `AC-001` 正常跨市场推荐

**Given** fixture 中有多个轻薄本及 USD、EUR、GBP 报价
**When** 用户请求“推荐 800 美元以内、有库存、适合出差的轻薄本”
**Then** 系统返回最多 3 个唯一商品，所有 selected offer 的 Landed Cost 不超过 800 USD，品类和库存均满足要求，每个结果都有报价和事实证据。

覆盖：`GLO-P0-001`–`GLO-P0-009`

### `AC-002` 硬约束先于排序

**Given** 一个超预算商品具有最高查询相关度
**When** 同一请求执行过滤和排序
**Then** 超预算商品在排序前被移除，且不能因高相关度重新进入结果。

覆盖：`GLO-P0-006`、`GLO-P0-007`

### `AC-003` 零命中不放宽预算

**Given** 所有目标商品的 Landed Cost 都高于预算
**When** 用户执行搜索
**Then** 返回 `NO_MATCH`、空结果和预算过滤计数；查询中的预算保持不变，不产生替代推荐。

覆盖：`GLO-P0-006`、`GLO-P0-010`

### `AC-004` 同款合并且报价不丢失

**Given** 三个 Provider 提供同一 `product_id` 的不同报价
**When** 系统聚合商品
**Then** 结果中该商品只出现一次，所有合法报价仍能按 Provider、市场和来源区分。

覆盖：`GLO-P0-004`、`GLO-P0-009`

### `AC-005` 未知费用不能伪装成预算内

**Given** 某报价缺少预算判断所需的运费或税费
**When** 请求包含硬预算
**Then** 该报价被标记为不可证明并从预算合格报价中排除，未知费用不按 0 计算。

覆盖：`GLO-P0-005`、`GLO-P0-006`

### `AC-006` 商品本体门

**Given** 数据中同时存在笔记本电脑、电脑支架、贴纸和替换电池
**When** 用户请求笔记本电脑
**Then** 只有笔记本电脑主体可以进入结果，文本高度相关的配件仍被过滤。

覆盖：`GLO-P0-006`、`GLO-P0-008`

### `AC-007` 证据约束

**Given** 某产品描述声称适合出差，但结构化证据只证明重量和续航字段
**When** 系统生成理由
**Then** 理由只能引用已验证字段，不得补写没有证据的耐用性、性能或其他能力。

覆盖：`GLO-P0-008`、`GLO-P0-009`

### `AC-008` 跨币种计算可追溯

**Given** 固定商品、费用分量和固定汇率快照
**When** 显示币种为 USD
**Then** 每个 Landed Cost 都能追溯到原币金额、费用分量、汇率和快照版本，重复执行结果相同。

覆盖：`GLO-P0-003`、`GLO-P0-005`、`GLO-P0-011`

### `AC-009` 非法意图引用 fail-closed

**Given** 解析器返回一个无法在原查询中定位的 Required 引用
**When** 系统校验解析结果
**Then** 不执行带伪造约束的搜索，返回可诊断的 `FAILED`，且不擅自改写用户请求。

覆盖：`GLO-P0-002`

### `AC-010` 脏记录隔离

**Given** 快照中有少量缺 ID 或缺来源记录，其余记录合法
**When** 系统加载快照
**Then** 脏记录被隔离并计数，合法记录继续执行；如果核心 manifest 或整体 schema 无效，则整次 run 为 `FAILED`。

覆盖：`GLO-P0-003`、`GLO-P0-004`

### `AC-011` 排序器降级不破坏硬门

**Given** scorer 抛出异常
**When** 硬约束过滤已经完成
**Then** 系统保持合格候选的稳定原序、标记降级，且不会恢复任何不合格商品。

覆盖：`GLO-P0-006`、`GLO-P0-007`

### `AC-012` 默认验收完全离线

**Given** 未配置网络、真实 LLM、OpenSearch、Redis 或 Postgres
**When** 执行完整 P0 测试命令至少两次
**Then** 两次均通过，输出商品顺序一致，且没有网络或外部服务调用。

覆盖：`GLO-P0-011`、`GLO-P0-012`

## 10. 非功能需求

| ID | 类别 | 要求 |
|---|---|---|
| `GLO-NFR-001` | 正确性 | 全部验收用例中硬约束违反率必须为 0%。 |
| `GLO-NFR-002` | 证据 | 最终输出中价格、库存、品类和推荐理由的证据完整率必须为 100%。 |
| `GLO-NFR-003` | 去重 | 最终结果内重复 `product_id` 数量必须为 0。 |
| `GLO-NFR-004` | 确定性 | 同输入、快照和配置连续执行 20 次，状态、商品顺序和金额必须一致。 |
| `GLO-NFR-005` | 性能 | 固定 seed 的 20,000 商品快照必须在预热后完成 100 次顺序请求，并记录环境、p50、p95 和 max；不含进程启动和可选真实模型。不同配置的本地结果为信息性，只有明确标记的参考 CI 才强制 p95 不超过 2 秒。 |
| `GLO-NFR-006` | 成本 | 默认模式产生 0 次付费模型和外部 API 调用；任何 live 模式必须显式开启并记录调用数。 |
| `GLO-NFR-007` | 可靠性 | 每个 run 只能有一个终态；`NO_MATCH` 与 `FAILED` 必须可区分。 |
| `GLO-NFR-008` | 可观测 | 每个 run 至少记录快照版本、阶段耗时、各硬门前后候选数、降级状态和终态。 |
| `GLO-NFR-009` | 安全 | fixture、日志和输出不得包含密钥；外部文本默认不可信，不能直接成为未验证事实。 |
| `GLO-NFR-010` | 隐私 | M0 不建立长期用户画像；测试查询和日志只使用非敏感样例。 |
| `GLO-NFR-011` | 可维护性 | 领域合同不依赖 FastAPI、LangGraph、OpenSearch 或具体模型 SDK；后续替换适配器不改变 P0 验收语义。 |

## 11. 架构资料追踪矩阵

| 来源主题 | 决策 | M0 落点或说明 |
|---|---|---|
| 对话式搜索 | Keep | 自然语言输入与结构化意图合同。 |
| 商品展示 | Change | M0 先交付结构化结果，不做 React 商品卡。 |
| 比价与推荐 | Keep | Canonical Product、Offer、Landed Cost、Top 3。 |
| 关税与运费 | Change | 使用版本化 fixture 和确定性费用分量，不接实时服务。 |
| 偏好与记忆 | Defer | M0 只使用当前 Query；长期记忆进入 M2。 |
| 实时可视化 / AG-UI | Defer | M1 以后接入，不能改变领域状态合同。 |
| 自主 ReAct AgentLoop | Drop as canonical | 与 README 的受控 StateGraph 目标冲突；M0 使用确定性领域管线，后续只考虑受控图。 |
| 多 Agent fork | Defer | M1 以后以受限 Provider Worker 形式实现。 |
| 独立三塔与 Query/User 加权 RRF | Drop as current design | 不作为当前实现主张；M0 Query-first，后续按 README 评估 shared-backbone 三视图。 |
| ItemSearch | Change | M0 使用确定性 Query scorer；后续替换为 Hybrid + reranker。 |

| Category Insight | Defer | M1；不得阻塞 M0 商品搜索。 |
| RAG 召回精排进阶 | Defer | 在基线 eval 和数据存在后进入 M2。 |
| FastAPI / Postgres 队列 | Defer | M0 先稳定领域合同；传输和持久任务进入后续 Plan。 |
| vLLM 推理服务 | Defer | 在真实模型需求、容量和成本基线明确后评估。 |
| 可观测体系 | Keep minimal | M0 保留 run、阶段、候选漏斗和降级诊断。 |
| Token 预算 / 熔断 / 安全护栏 | Defer with boundary | M0 不调用真实服务；合同需预留失败与降级状态。 |
| Rubric 评测 | Keep | M0 先做确定性验收集，不宣称生产推荐指标。 |

## 12. 风险与缓解

| 风险 | 影响 | M0 缓解 |
|---|---|---|
| README 描述目标态但无对应代码 | 容易误判完成度 | 明确从零构建，并以 Spec 验收。 |
| 没有真实商品数据 | 无法证明生产覆盖率 | 建立小而完整的版本化 fixture，仅验证业务不变量。 |
| 自然语言解析存在歧义 | 可能制造错误硬约束 | source span 校验、Fake 解析器合同、fail-closed。 |
| 税费与关税规则复杂 | 到手价可能不可信 | M0 使用明确费用分量；未知即未知，不做推测。 |
| 相关度质量难量化 | 容易过早优化模型 | 先用确定性 scorer 和固定 expected order 建立基线。 |
| 全量架构过大 | 首个可运行版本迟迟无法完成 | 把生产基础设施和 Agent 能力分阶段接入。 |

## 13. 已确认决策与后续开放项

### 13.1 M0 已确认决策

- `D-001`：按从零构建处理，当前工作区没有可复用源码。
- `D-002`：README 是目标态参考，PNG 是历史或专题材料。
- `D-003`：首个里程碑是本地可复现的垂直切片，不是全量架构。
- `D-004`：默认验收不使用真实 LLM、网络或外部数据库。
- `D-005`：固定商品池、硬约束、Query-first 和带证据 Top 3 是 M0 主路径。
- `D-006`：长期记忆、模型训练、完整 RAG、生产基础设施和复杂前端延期。
- `D-007`：输入使用两阶段校验；快照和币种兼容性错误是带 run ID 的 `FAILED`。
- `D-008`：预算按查询币种精确比较；未声明币种时继承展示币种。
- `D-009`：M0 无条件排除非在售或到手价不完整的报价，预算门仅在存在预算时启用。
- `D-010`：最小可信运行记录是应用内 RunJournal；外部事件投影属于 M1。

### 13.2 不阻塞 M0 的后续开放项

- 真实商品数据的来源、许可和更新机制。
- 真实 LLM 与 embedding 模型供应商。
- 生产环境中的汇率、税费和关税数据源。
- 是否以 HTTP、事件流或其他界面作为第一个外部传输层。
- OpenSearch、Postgres、Redis 和部署平台的容量设计。

- [x] 所有 `GLO-P0-*` 已实现并能追溯到代码和测试。
- [x] `AC-001` 至 `AC-012` 全部自动化并通过。
- [x] 默认测试已证明没有真实网络、LLM 或外部数据库调用。
- [x] 硬约束违反率、证据完整率、去重和确定性指标满足 NFR。

- [x] 没有未说明的降级、自动条件放宽或无证据产品陈述。
- [x] README 已更新为真实完成度，不再把目标态写成已实现事实。

## 16. 变更治理

1. 改变用户可见行为、硬约束语义、输出合同或验收门槛，必须先修改本 Spec。
2. 只改变内部实现且不影响本 Spec 的决策，用 ADR 记录。
3. 每个实现任务必须引用至少一个 `GLO-P0-*` 或 `GLO-NFR-*`。
4. 新技术不能仅因架构图出现而进入 M0；必须能解决已批准需求。
5. M0 完成前，后续能力可以调研，但不能破坏离线、确定性和硬约束基线。
